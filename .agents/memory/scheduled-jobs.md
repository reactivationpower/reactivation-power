---
name: Scheduled jobs on autoscale and Vercel
description: Why daily jobs use a slot-claim table plus several triggers (in-process ticker, external cron, Vercel Cron), how partial runs continue, and why the scheduler is off in the workspace
---
- **Rule:** a day's job is a slot `(job, ET date)` claimed by unique insert in `cron_runs`. The in-process ticker, the Bearer HTTP route and Vercel Cron all claim the *same* slot; only explicit `?force=1` / admin "Run now" bypass it (and those still refuse while a run is in progress). Add jobs to the `CRON_JOBS` registry only.
- **Why:** the Replit deployment is autoscale (scales to zero) and Vercel has no process between requests, so a timer alone cannot guarantee a 6 AM run; an external cron alone is a single point of failure. Several triggers + one claim gives on-time runs without ever double-retrying a customer's cards.
- **Vercel Cron decisions:** schedule each daily job at *both* UTC hours its ET slot can fall on (DST) and let the slot claim make the wrong-hour call a no-op — do not try to compute DST in cron syntax. One consolidated five-minute route rather than several parallel crons, because of the shared connection budget; it also catches up missed daily slots because Vercel does not retry a failed cron call, and it runs off the hour so the daily cron claims its slot first.
- **Time budget / continuation:** every run has a deadline below the function limit and jobs stop only *between* items; a run that stops early is stored as `partial`, re-claimable, with the previous summary passed back as `prior`. Progress must be derivable from the DB plus that summary, and the summary is checkpointed into the running row as it grows (a killed function is continued from its last checkpoint by the stale take-over): the billing pass records the customers it attempted so a continuation never retries a declined card before reaching the tail; multi-step jobs record each step's result and re-run only a step that was itself incomplete. Manual "Run now" continues a partial run before it starts a fresh one. Demo reset cannot stop mid-practice, so it defers a practice when little budget is left.
- **After-response work:** anything previously fire-and-forget (`setImmediate`, `void promise`) must go through the after-response helper (Vercel `waitUntil`) with a bounded deadline, or be awaited. `waitUntil` is a no-op off Vercel.
- **Readiness:** the sales-automation "Scheduler running" rule reads one capability stamped by whichever scheduler is alive (pg_cron or Vercel Cron, distinguished by `source`); never add a second rule.
- **How to apply:** keep the scheduler **off in the workspace** and never on Vercel: the demo reset rebuilds the *shared* Supabase demo. Card declines inside a retry are a normal summary; only thrown errors alert the super admin.
