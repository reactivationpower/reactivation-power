# Reactivation Power

Training portal + patient-reactivation dialer for healthcare/service businesses: learners watch course videos, run call queues from imported contact lists, and admins manage courses, participants, scripts, and payment links. Ported from a Vercel/Next.js app into this workspace.

## Run & Operate

- **Vercel hosting (in preparation):** `docs/vercel-hosting.md` has the project settings, routing, Preview-safety rules and the full environment variable table. Vercel runs the same Express app through `api/index.mjs` → `artifacts/api-server/src/vercel.ts`; Replit keeps `src/index.ts` (`app.listen`, scheduler, boot-time admin seed). On Vercel `STRIPE_MODE` must be set, email uses `RESEND_API_KEY`, and Preview deployments (shared database) never run jobs, send email/texts or use live Stripe (`lib/deployment-safety.ts`). Stripe test mode never falls back to live keys anywhere.
- Customer-facing email links must use `https://reactivationpower.com`, not a Replit hostname. Keep the shared `APP_URL` set to this canonical origin; existing link builders preserve their paths and tokens.

- Workflows: `artifacts/api-server: API Server` (Express, `/api/*`) and `artifacts/reactivation-power: web` (Vite SPA at `/`). Restart both after server changes. Both `dev` scripts run `scripts/free-port.mjs` first, which terminates any leftover process still listening on `$PORT` (logged as `[free-port] port … is held by stale pid …`) so a restart can never fail with `EADDRINUSE` while an old build keeps answering; production `start` scripts do not run it. If a workflow log ever shows "address already in use" anyway, compare the listener's start time with `dist/index.mjs`'s mtime before debugging code.
- `pnpm run typecheck` — full typecheck. Verify artifacts with `pnpm --filter @workspace/<pkg> run typecheck`, not `build`.
- Data: **everything lives in the one Supabase project** `jbdymqqpolkoevyypjxd`, in development and production alike. Two access paths: the REST/Auth client with the service role (`SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`) for the older tables (participants, payment_links, courses, scripts …), and a direct Postgres connection through drizzle (`lib/db`, `SUPABASE_DB_URL` = the Session-pooler URI from the Supabase dashboard) for the billing/agreement/email/commission/cron/notification tables. `lib/db` throws at startup if `SUPABASE_DB_URL` is unset. There is no Replit database; `DATABASE_URL` is not read anywhere. Media (videos, thumbnails, attachments): Vercel Blob (`BLOB_READ_WRITE_TOKEN`).
- Adding or changing a drizzle table: edit `lib/db/src/schema/*.ts` (new tables call `.enableRLS()` — the app connects server-side as `postgres`, so no policies are needed), then `pnpm --filter @workspace/db run generate --name <snake_case>` to write a migration under `lib/db/migrations/`, review the SQL, and `pnpm --filter @workspace/db run migrate` to apply it to Supabase (tracked in `drizzle.__drizzle_migrations`). Commit the migration. **Never run `drizzle-kit push`** against Supabase: the public schema holds tables drizzle does not model and push would try to drop them (`tablesFilter` in `drizzle.config.ts` is a second guard). The same command applies to production because dev and prod share the database.
- Other env: `SESSION_SECRET` (cookie signing), `SUPER_ADMIN_EMAIL` (bootstrap super admin, seeded at API start; optional `SUPER_ADMIN_INITIAL_PASSWORD` creates it ready to sign in), `DEMO_PASSWORD`, `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` (served to the SPA by `GET /api/config`), `GHL_*` (GoHighLevel booking), `CRON_SECRET`, `RESEND_FROM` / `RESEND_WEBHOOK_SECRET` (see Transactional email).
- Original Next.js source is kept in `.migration-backup/` for reference.
- **Scheduled jobs** (`lib/cron/jobs.ts` registry, `lib/cron/slots.ts`, `lib/cron/scheduler.ts`, `routes/cron.ts`, `actions/cron.ts`, card on `/admin/payments`): **billing retry daily at 6:00 AM ET**, **demo reset daily at 3:00 AM ET**. To change a time, edit `hourEt` in `CRON_JOBS`. Each day's run is a *slot* keyed by `(job, due_key = ET date)` in `cron_runs` (Supabase via drizzle; schema changes ship as migrations, see Data above); whoever claims the slot first runs it, everyone else is a no-op — so the two triggers below can overlap safely. All claims (slot, `?force=1`, admin "Run now") take a per-job `pg_advisory_xact_lock`, so no two passes of a job ever run at once. **Trigger 1 — in-process scheduler**: on when `NODE_ENV=production` (`CRON_SCHEDULER=on|off` overrides; keep it off in the workspace — the demo reset rebuilds the *shared* Supabase demo). Every instance ticks every 5 min and claims the current slot; a run stuck `running` for 30 min is treated as a crash and re-claimed. **Because the deployment is autoscale, an idle app has no instance awake to tick**, so a quiet night only runs the job when the first request of the day arrives. **Trigger 2 — external cron (required for an on-time run)**: point a scheduler at `GET https://reactivation-power.replit.app/api/cron/billing-retry` at 6:00 AM ET and `GET …/api/cron/demo-reset` at 3:00 AM ET with header `Authorization: Bearer <CRON_SECRET>` (cron-job.org, GitHub Actions `schedule`, or a Replit Scheduled Deployment in a separate project running `curl -fsS -H "Authorization: Bearer $CRON_SECRET" <url>`). The request wakes an instance and claims the same slot (`{ ok: true, skipped: true }` if it already ran); add `?force=1` to re-run outside the slot. The production deployment must be public for the external caller to reach it. **Visibility** (super admins only — reps do not see the card or the `cron` actions): every run (scheduler, external, admin "Run now") is logged and shown on the Scheduled jobs card with its summary; a slot still un-run 2 h after its hour shows an amber **Overdue** badge, a thrown job turns the card red and emails `SUPER_ADMIN_EMAIL` (`cron_failed` template). Declined cards inside a billing retry are a normal summary, not a failure.

## Call scripts (content as code)

- **Start every script change at `docs/SCRIPT_STYLE_GUIDE.md`.** It holds the voice rules, the step skeleton, token and routing rules, before/after examples, and the batch-rewrite loop.
- Script flows (Supabase `script_flow_steps` / `script_flow_choices`) are mirrored in the repo at `artifacts/api-server/content/flows/<niche-slug>.json` plus `general.json` (shared, `niche_id` null). The player resolves a niche row with the same `step_key` over the general one.
- Commands (`pnpm --filter @workspace/api-server run …`): `flows:export` (DB → JSON), `flows:lint [slug…]` (style rules, exit 1 on errors), `flows:apply [--dry-run] (--all | slug…)` (JSON → DB, idempotent upsert matched by step_key / from+to, never deletes, refuses bad routes or unknown tokens). Tooling lives in `artifacts/api-server/scripts/flows/` and runs with plain `node` (type stripping). `flows:lint --quiet` is registered as the `flows-lint` validation step and runs with `test` and `typecheck` on task completion, so a flow JSON with lint errors cannot be merged.
- `flows:check [--quiet] [slug…]` compares the live database with `content/flows/` in both directions (steps by step_key, choices by from+to paired in sort_order — the same matching as apply) and exits 1 on any text difference or a slug present on only one side; niche-row attributes (is_active, sector, sort_order) print as notes only. It is **not** a validation step and is deliberately run by hand: it needs the Supabase service-role key at validation time, and all task branches share one live database, so an in-flight task that has applied its niche would fail every other task's validation. Run it before starting a script rewrite (so the JSON you edit is what the phones run), right after `flows:apply`, and whenever a flow may have been edited in the admin UI or by SQL. `DRIFT` = fix by `flows:apply <slug>` if the file is right, or `flows:export <slug>` + `flows:lint` + commit if the database is right.
- General + Skin Tightening are the rewritten reference; other niches are exported as-is and still fail lint until their batch rewrite. Concern chips for the question screens, the CSV keyword→niche matcher and the public service catalog live once in `lib/niche-catalog` (`@workspace/niche-catalog`), imported by both the web app and the api-server (including `flows:lint`). Add a new niche there only — a unit test in the api-server fails if a per-artifact copy of `concern-options`/`niche-match`/`service-catalog` reappears. The other pure helpers both sides need (`types`, `script-merge`, `phone`, `format`, `call-time`, `lazy-time`, `lead-validation`, `notes-text`, `opportunity`, `us-timezones`, `analytics-types`, `email-templates`) live once in `lib/shared` (`@workspace/shared/<module>`); the same test fails if a copy reappears in either `src/lib`. Only `notes-html` (needs `sanitize-html`, server-only) stays in the api-server.

- Admin UI: `/admin/emails` → "Account emails" tab (`components/admin/transactional-emails.tsx`): live preview, test send, recent-sends log. Actions: `mail.listTransactionalTemplates / sendTestEmail / listEmailLog` (super admin).

Delivered through the `billing_notifications` outbox (Supabase via drizzle, `lib/db/src/schema/billing-notifications.ts`): unique on (slot, invoice) — `slot` is a generated column equal to the type except that `access_restored` and `payment_received` share the `paid` slot — so racing webhooks/cron send exactly once and a recovering customer gets one email for one payment; the template data is stored on the row and failed sends are retried (up to 5 attempts) by `retryFailedNotifications()` from `GET /api/cron/billing-retry`. ## Billing (customers, payment links, subscriptions)

- `payment_links` (managed through the Supabase REST client) remains the link identity + `status` flag; the billing tables sit beside it in the same Supabase database but are accessed through drizzle (`lib/db/src/schema/billing.ts`, `SUPABASE_DB_URL`): `customers` (contact/business fields, `stripe_customer_id`), `payment_link_terms` (PK = Supabase link id; type one_time/subscription, rep, setup/monthly cents, intent ids, subscription id/status, next payment, agreement start/end) and `customer_cards` (payment method id, fingerprint, brand, last4, rank primary/secondary). Folding `payment_link_terms` into `payment_links` is a possible later cleanup now that both are in one database.
- Admin "New customer" creates the customer record and either a full-price link (embedded Checkout, unchanged) or a subscription link (setup fee defaults to the monthly amount, editable/waivable). Links are stamped with the creating admin (`rep_id`, `rep_name`).
- Subscription checkout (`/pay/:token`, `components/landing/subscription-checkout.tsx` + `actions/subscriptions.ts`): step 1 PaymentIntent for the setup fee with `setup_future_usage` (SetupIntent when waived) → primary card; step 2 SetupIntent → backup card. The server compares Stripe card fingerprints and detaches a duplicate second card with a clear error. Then it creates the Stripe Subscription (product tagged `metadata.rp_product=access`, monthly price, `trial_end` = setup paid + 30 days, primary as default PM), marks the Supabase link paid, provisions portal accounts, and sets agreement start = trial end, end = +12 months. Supabase `status='paid'` is set only when the subscription is fully activated; `setup_paid_at` marks the intermediate "awaiting backup card" stage.
- Stripe mode: `lib/stripe.ts` resolves keys once at startup (`initStripe()`); the `stripe` export is a proxy over the resolved client. Test mode = Replit Stripe integration sandbox keys (fallback `STRIPE_TEST_SECRET_KEY`/`STRIPE_TEST_PUBLISHABLE_KEY`); live = `STRIPE_SECRET_KEY`/`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`. Unset `STRIPE_MODE` → test in the workspace (startup fails if no sandbox keys — it never falls back to live), live in the Replit production deployment; `STRIPE_MODE=test|live` forces it and is required on Vercel. The admin Payments page and public pay page show a "Stripe test mode" badge/banner. Sandbox and live are separate Stripe accounts, so links created in one mode cannot be completed in the other.
- **Webhooks & dunning** (`routes/webhooks-stripe.ts`, `lib/billing/dunning.ts`): register `https://<app>/api/webhooks/stripe` in the Stripe Dashboard for each mode with events `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`, `charge.refunded`, and store the signing secret as `STRIPE_WEBHOOK_SECRET` (live) / `STRIPE_TEST_WEBHOOK_SECRET` (sandbox) — the route answers 503 until it is set. Every event id is claimed in `stripe_events` first, so redeliveries are acknowledged without re-running. The ledger is `payment_history` (charges, declines, refunds, cancellations, date changes; card rank/last4, Stripe ids, source webhook|dunning|cron|admin, acting admin).
- **Failed-payment policy**: a declined invoice is retried immediately on the other card (`stripe.invoices.pay` with that payment method), **one attempt per card per invoice** — the retry is chosen from every card already recorded as declined on that invoice, because each attempt we make produces another `invoice.payment_failed` event. Subscription status events are reconciled against fresh Stripe state (live status + open invoices) before blocking or restoring, since webhooks arrive out of order. If both cards fail the customer becomes `past_due` (`billing_blocked_at`, `billing_issue`), and the owner **and all staff** are locked out everywhere a portal cookie is accepted (`getCurrentParticipant()` redirects to `/login?reason=billing`; `/api/media`, `/api/progress` and portal RPC use `getAllowedSession()` / `participantIfBillingAllows()` and answer 401), the login action returns `billing` info, and the login page shows the notice linking to `/billing`. Any successful payment (ours, Stripe's, or a card update) restores access. `GET /api/cron/billing-retry` (Bearer `CRON_SECRET`) re-attempts every open invoice on both cards; the in-process scheduler runs it daily at 6 AM ET (see Scheduled jobs under Run & Operate). **Turn off Stripe's own retries** (Dashboard → Settings → Billing → Subscriptions and emails → Manage failed payments → "Do not retry") so the app is the only thing retrying; handlers stay idempotent if a Stripe retry slips through. Customers are linked to the portal owner via `customers.participant_id` (stamped by `provisionAccounts`, backfilled from Supabase `payment_links.participant_id` on first check); demo accounts are never gated.
- **Admin billing actions** (`actions/billing.ts`, any active admin; `components/admin/billing-panel.tsx` on `/admin/payments/:id`): refund full/partial (validated against Stripe's remaining refundable amount), cancel at end of term (`cancel_at` = agreement end) or immediately (locks the portal), undo a scheduled cancellation, change the next billing date (`trial_end` + no proration, so the cycle re-anchors), and "Retry both cards now". One-time purchases and setup fees are also written to the ledger (`recordIntentPayment`) so they can be refunded from the same panel.
- **Commissions** (`lib/db/src/schema/commissions.ts`, `lib/billing/commissions.ts` + pure rules in `commission-rules.ts`, `actions/commissions.ts`, page `/admin/commissions`): every `payment_history` row that is a collected payment (`invoice_paid`/`succeeded`) or refund gets one `commission_entries` row (unique on `payment_history_id`, so generation is idempotent), created inside `recordHistory` and attributed to the rep stamped on `payment_link_terms`. Sale type: one-time link → `full_price`; subscription link → `monthly` when the row has a Stripe invoice id, else `setup_fee`; refunds are negative entries at the rate the original sale used (`refund_of` keeps the original type). The rate is frozen from the rep's `default_commission_rate` at the time of the sale (`default_rate_percent`) — changing a rep's default later never rewrites history. Super admins can override rate *or* amount (with a note), clear the override, mark entries paid out / undo, and "Generate missing entries" backfills older ledger rows (rows without a link or rep are skipped, not invented). Sales reps see only their own entries; the server forces the rep filter regardless of query params. Generation failures are logged and never fail payment handling.

- **Super-admin billing dashboard** (`/admin/billing`, `pages/admin_billing.tsx`; loader in `routes/pages.ts` → `lib/billing/dashboard.ts`, pure `computeBillingDashboard` is unit-tested): cash collected (net of refunds), collected/failed counts for a `?from=&to=` day range (UTC, default last 30 days); MRR = `monthly_cents` of subscriptions in active/trialing/past_due and not canceled; outstanding = latest failed attempt per invoice with no succeeded row, excluding canceled customers; upcoming = `next_payment_at` within 30 days unless `cancel_at` comes first. Each customer row uses the link that governs billing today (delinquent subscription > live subscription > completed agreement > newest link; a past-due row points at the link that declined) and links to `/admin/payments/:id` (the customer record: status, cards primary/backup, ledger).

Set as shared env vars in Replit; **the same two values must be added in Vercel** for production. Missing key = PostHog never starts; it never starts in tests either.

Never call `identify`.

## Architecture decisions

- **Portal sign-in (owners and callers):** email + password + a six-digit email code (5-minute code life, 5 wrong tries). After a correct code, that browser is remembered for that person for a fixed **48 hours** from the code entry (`portal_auth_devices` + an HttpOnly signed per-person `tp_device_*` cookie, bound to the password revision); during that time sign-in is email + password only. Manual log out forgets that browser; a password change/reset forgets every browser; inactivity logout does not. Portal and admin sessions log out after **30 minutes** without real activity (server and browser both enforce it); a "Still there?" box with a "Stay signed in" button appears 1 minute before. Both sales demo accounts are exempt from codes and inactivity logout. Admin sign-in has no remembered computer.
- **Authentication retention:** `auth-cleanup` runs daily at **4:00 AM ET** through the same claimed job registry, dashboard, and failure alerts as billing/demo jobs. External schedulers can wake it via `GET /api/cron/auth-cleanup` with `Authorization: Bearer <CRON_SECRET>`; this is needed for an on-time run on autoscale. Retired portal login/password challenges, obsolete rate-limit windows, and expired/revoked/30-minute-idle security sessions, and expired/revoked remembered computers are retained for **one day after retirement**, then deleted. Current counters persist their window duration; legacy counters conservatively use the former maximum one-hour window. Live codes, current counters, active sessions, credentials, and historical `sessions`/`activity_events` are not deleted. Missing challenge/session rows remain invalid; no activity endpoint may recreate them.

- Actions are exposed by name through one RPC route rather than rewritten as REST; page data goes through per-page loaders instead of exposing the data layer generically. Auth is enforced at the route level (cookies `tp_session` / `tp_admin`) in addition to the checks inside the actions.
- A `redirect()` from an action/loader is returned as JSON and followed client-side with a full navigation (cookies are set server-side). Only same-origin path redirects are followed (`safeRedirect`).
- `revalidatePath` is a no-op; components call `router.refresh()` after mutations so `usePageData` re-fetches.
- Frontend and API share one origin through the workspace proxy; CORS is intentionally not enabled.

## Gotchas

- Files under `artifacts/reactivation-power/src` and `artifacts/api-server/src/actions|lib` are largely CRLF and many carry `// @ts-nocheck`; typecheck passing does not guarantee no undefined identifiers — read diffs.
- Loaders serialize `Map`s as plain objects keyed by id; pages must use `obj[id]`, not `.get(id)`.
- `/api/upload/token` and `/api/upload` require the admin cookie; server-side fallback uploads are capped at 4 MB to fit Vercel's 4.5 MB request limit (large files go direct to Blob from the browser); see `src/lib/request-limits.ts`.
- Admin participants page lists owners only (staff nested under their owner), so its count is lower than the dashboard's total viewers — this matches the original app.
